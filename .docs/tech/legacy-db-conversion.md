# Legacy Database Conversion

Removing the built-in subscriptions and the embedded CLIProxyAPI adapter removed
migration entries and two credential columns from the schema, so this build
cannot open a database written by the last release that still shipped retired
migration `0003_remove_observation_fresh_until`. Operators have exactly two
supported paths:

- **Convert offline** with `gpt-load convert-legacy-db` and keep groups,
  encrypted credentials, access keys, quota state, and settings; request logs,
  usage history, and debug captures are not carried over.
- **Start with a fresh database** and reconfigure everything by hand.

There is no in-place migration, no compatibility layer, and no automatic
deletion. The converter is the only migration path, and it only runs as an
offline command against a stopped database.

## Command

```bash
gpt-load convert-legacy-db --source <legacy.db> --target <new.db>
```

- Both flags are required and there is no key flag: the encryption key is never
  read, copied, or generated by the command.
- `--source` must be an existing SQLite **file**; `:memory:` and non-SQLite DSNs
  are refused. The source is opened read-only (`mode=ro`) and snapshotted with
  SQLite's own `VACUUM INTO`, so committed WAL pages are included.
- `--target` must be a SQLite file path that does not exist. An existing target
  is refused, never overwritten or merged. The published database is one file in
  `journal_mode=delete`, published with a no-replace atomic link into the target
  directory; a failed run leaves no target behind.
- The command prints the copied row count per retained table, the retired columns
  it skipped, a fixed notice that request/usage logs and debug captures were not
  migrated, and a reminder to copy `encryption.key`.
- Every precondition below is checked against the **source** before anything is
  copied, and the whole result set is rewritten wholesale. A source that fails
  any check produces no target file at all, so a partial conversion is not a
  state an operator can end up in.

## Supported Source

Acceptance is the conjunction of five independent proofs, all read from the
source: the pinned ledger, the declared table and column shape, table integrity,
ordinary (non-subscription) groups, and the absence of stored subscription
material. The checks run in that order after the writer gate, so a missing table
or column is reported as itself rather than as the foreign-key damage it would
cause later.

The ledger check is a **literal pinned list**, not a derivation from the running
code: the converter carries its own copy of the last legacy release's chain, so a
future migration can never be reinterpreted as part of the old chain.

| Ledger | Accepted |
| --- | --- |
| `0001_initial`, `0002_access_key_cost_limits`, `0003_remove_observation_fresh_until`, then `0004_usage_stats_group_activity_index` … `0025_affinity_diagnostics` | required; every entry must be present |
| `0009_price_multipliers` | **optional**; accepted when the source applied it before that migration was retired |

Retired IDs are optional because the chain skips retired migrations instead of
deleting their ledger rows, so a database that applied `0009_price_multipliers`
keeps that row forever. `0009_price_multipliers` is the only retired ID the
converter accepts, and only as an addition: any other unknown ID, a duplicate, an
out-of-order entry, or a missing required entry is refused.

The source **schema** is pinned in both directions per retained table: every
current column must exist, and any other column must be a retired column
(`credentials.auth_state`, `credentials.auth_error_code`). The retired
subscription tables are declared from
`internal/storage/migrations/legacy_retired_schema.go`, the models that
reproduce the historical DDL, so the converter no longer guesses what a real
legacy database looks like.

| Refusal | Meaning |
| --- | --- |
| ledger mismatch | A required entry is missing, or an ID outside the pinned chain and the retired set is present. |
| undocumented table | A source table is neither migrated nor on the drop list; the converter refuses to guess. |
| extra or missing column | The declared schema cannot be reproduced in this release. |
| non-empty `-wal` / present `-journal` | A writer still holds the database, or a transaction was interrupted. Checked before the source is opened and again after the snapshot. |
| missing retained table | A table the supported legacy schema declares is absent; copying would publish an empty table and silently lose the rows. |
| `integrity_check` / `foreign_key_check` failure | The source is damaged; repair or restore it first. |
| subscription group | A group uses a retired connection type (`subscription`, `oauth`), a deleted subscription channel (`codex`, `antigravity`, `grok`), or a channel this release no longer defines. |
| stored subscription rows | Any row at all in `credential_stages`, `credential_observations`, or `credential_reset_operations`. |
| subscription credential state | `credentials.auth_state` is not `ready`, or `credentials.auth_error_code` is non-empty. |

The last three rows are deliberate: subscription material is refused rather than
silently dropped. Row count decides the table check, not reachability or state:
one stored row in any of the three retired tables is enough, because the
conversion drops those tables and the stored data could not be recovered. An
empty retired table is the normal API-key-only state and is accepted. Only
`connection_type=api_key` groups are copied; a group whose channel this release
no longer defines is refused as a subscription group rather than dropped.

Writer detection is a best-effort gate, not a lock. An empty `-wal` or a `-shm`
side file is not treated as a writer because a read-only open creates them, so
stopping the legacy instance remains the operator's responsibility. The gate
runs twice — before the source is opened, and again after the `VACUUM INTO`
snapshot — so a writer that appears mid-conversion is still caught.

The published target is proven, not assumed: every copied table must match its
source row count and identity set, the target must declare no retired column,
its `AUTOINCREMENT` counters must not fall below the source counters, and
`PRAGMA foreign_key_check` plus `PRAGMA integrity_check` must both pass. Any
failure aborts publication.

## What Is Migrated

Copied: `groups`, `credentials` (ciphertext, fingerprints, `secret_version`,
IDs), `access_keys`, `access_key_cost_limit_rules`,
`access_key_cost_limit_states`, `system_settings`, `model_prices`,
`control_operations`, `jobs`, `agent_credentials`,
`agent_change_proposals`.

Not copied, with no replacement: `request_logs`, `request_log_attempts`,
`credential_attempt_stats`, `credential_observations`,
`credential_reset_operations`, `credential_stages`, all `debug_capture*` tables,
`usage_stats`, `usage_attempt_stats`, `usage_aggregation_journal`,
`usage_attempt_aggregation_journals`, and `schema_migrations`. Retired columns
`auth_state` and `auth_error_code` are dropped and reported.

`credential_attempt_stats` is **dropped, not retained**: it is per-credential
attempt statistics, so it is history like the usage tables around it. Do not
expect its rows in the converted database.

The published database is what the application opens, so it will run its own
migration chain on first start; the ledger is rebuilt, not copied. The copy also
carries each table's `sqlite_sequence` high-water mark: a legacy row ID that was
deleted (but referenced by old request logs, exports, or backups) is not handed
out again by the converted database.

## Key Material

The converted database stores credential ciphertext written with the legacy
installation's master key. That key must reach the new `DATA_DIR` unchanged:

- copy the original `encryption.key` file into the new `DATA_DIR`, **or** keep
  the same `ENCRYPTION_KEY` value in the new environment.

If neither happens the gateway generates a new key and fails credential loading
with a fingerprint mismatch; existing credentials stay undecryptable. Copy the
legacy `auth.key` (or keep the same `AUTH_KEY`) only if the management key must
stay the same.

## Operator Runbook

Every step is offline work on copies. Nothing below merges new data back into the
legacy database, and nothing below changes the running legacy instance in place.

1. **Confirm the source.** Run the converter against a **copy** first. A refusal
   message tells you which prerequisite fails; fix the cause (for example delete
   or migrate subscription groups in the legacy instance) or stay on the legacy
   release. Do not edit `schema_migrations` or drop tables by hand.

2. **Stop the old instance and confirm no writers.**

   ```bash
   docker compose -p gpt-load stop -t 30 gpt-load
   docker ps -q --filter volume=gpt-load_gpt-load-data   # must print nothing
   ls -l /var/lib/docker/volumes/gpt-load_gpt-load-data/_data/ | grep -E 'wal|journal'
   ```

   A non-empty `gpt-load.db-wal` or a `gpt-load.db-journal` means something still
   writes; find and stop it before continuing.

3. **Back up the whole data directory.** Keep the database, `-wal`, `-shm`,
   `auth.key`, `encryption.key`, and the env/compose configuration as one set:

   ```bash
   data=/var/lib/docker/volumes/gpt-load_gpt-load-data/_data
   archive=/secure/backups/gpt-load-legacy-$(date +%Y%m%dT%H%M%SZ).tar
   tar -C "$data" -cf "$archive" .
   tar -tf "$archive" >/dev/null   # verify the archive is readable
   sqlite3 -readonly "$data/gpt-load.db" ".backup '/secure/backups/gpt-load-legacy.db'"
   ```

   The tarball is the rollback set; the separate `.backup` file is the converter
   input, so conversion never touches the volume. Copy `.env` and
   `docker-compose.yml` alongside them. Space, permissions, and archive
   verification follow the same rules as
   [SQLite maintenance and recovery](../../docs/sqlite-maintenance.md).

4. **Convert into a new data directory or volume.** Use the new image and a new
   directory; never the legacy directory:

   ```bash
   mkdir -p /srv/gpt-load-new/data
   docker run --rm --network none \
     -v /secure/backups:/backup:ro -v /srv/gpt-load-new/data:/app/data \
     gpt-load:<new-tag> \
     convert-legacy-db --source /backup/gpt-load-legacy.db --target /app/data/gpt-load.db
   ```

   Check the printed row counts against the legacy counts for groups,
   credentials, and access keys before going further.

5. **Move the key material.** Copy the legacy `encryption.key` into the new data
   directory, or set the same `ENCRYPTION_KEY` in the new environment. Do not let
   the gateway generate a new key.

6. **Start the new version on the new volume, on a spare port.**

   ```bash
   docker run -d --name gpt-load-new --network none \
     -e HOST=127.0.0.1 -e PORT=3101 -e DATA_DIR=/app/data \
     -v /srv/gpt-load-new/data:/app/data gpt-load:<new-tag>
   docker logs gpt-load-new | grep -E 'startup.ready|startup.failed'
   ```

7. **Verify before switching traffic.** Health alone is not verification:

   - sign in with the management key;
   - open several groups and confirm credentials are readable and decryptable;
   - send one non-streaming and one streaming request through a real group;
   - confirm existing access keys authenticate and their quotas still show the
     pre-conversion usage values;
   - confirm subscription channels are absent and no group lost its models.

8. **Switch traffic** only after step 7 passes: publish the new port in the
   ingress configuration, then repoint clients.

9. **Rollback** is the untouched legacy image plus the untouched legacy volume:
   start the legacy container again on its original port and revert the ingress
   entry. Requests served by the new instance after the switch are **not** merged
   back into the legacy database; keeping them means re-running the conversion
   from the legacy backup plus manual repair, which is not a supported path.

### Deployment script boundary

`scripts/deploy.sh` is for in-place upgrades: it loads the new image, stops the
container, archives the data, repoints Compose, and restarts on the **same**
existing volume. It does not convert a database and it must not be pointed at the
legacy volume for this upgrade, because the new image would only refuse to start.
Run the conversion first, deploy the new version against the converted volume,
and keep the legacy volume and backup out of the script's reach.

## 中文说明

删除内置订阅与嵌入式 CLIProxyAPI 后，schema 少了迁移条目和两个凭据列，本构建
无法直接打开最后一个仍携带退役 migration `0003_remove_observation_fresh_until`
的版本写出的数据库。只有两条受支持路径：

- **离线转换**：`gpt-load convert-legacy-db` 保留分组、加密凭据、访问密钥、
  限额用量与设置；请求日志、用量历史和 debug capture 不迁移。
- **全新数据库**：手工重建全部配置。

没有原地迁移、兼容层或自动删除；转换器是唯一的迁移入口，且只在数据库停机时
作为离线命令运行。

```bash
gpt-load convert-legacy-db --source <legacy.db> --target <new.db>
```

- 两个参数都必填，没有 key 参数：命令不读取、不复制、不生成加密密钥。
- `--source` 必须是已存在的 SQLite **文件**，以只读方式打开并用 `VACUUM INTO`
  取快照（包含已提交的 WAL 页）。
- `--target` 必须是不存在的 SQLite 文件。已存在的目标会被拒绝，绝不覆盖或合并；
  发布结果是 `journal_mode=delete` 的单文件数据库，通过同目录硬链接原子发布，
  失败不会留下目标文件。
- 命令会打印每张保留表的拷贝行数、被跳过的退役列，并提示复制 `encryption.key`。
- 下方所有前置条件都在拷贝前针对**源库**校验，结果整体重写。任何一项不通过的
  源库都不会产生目标文件，因此操作者不会停在部分转换的状态里。

### 受支持的源库

接受一个源库等于同时证明五件事，且全部读自源库：固定台账、声明的表与列结构、
表级完整性、普通（非订阅）分组，以及不存在已保存的订阅材料。它们在写入者检查
之后按此顺序执行，因此缺失的表或列会被如实报告，而不是表现为它后面引发的
外键损坏。

台账校验是一份**字面量固定清单**，不是从运行代派生：转换器自带最后发行版本
的迁移链副本，未来新增的 migration 不会被重新解释为旧链的一部分。

| 台账                                                                                                                         | 要求                                   |
| ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `0001_initial`、`0002_access_key_cost_limits`、`0003_remove_observation_fresh_until`，以及 `0004_usage_stats_group_activity_index` … `0025_affinity_diagnostics` | 必填，缺任何一条即拒绝                 |
| `0009_price_multipliers`                                                                                                     | **可选**；源库在该 migration 退役前执行过时接受 |

退役 ID 之所以可选：迁移链跳过退役 migration 而不删除其台账行，因此在
`0009_price_multipliers` 被移除前执行过它的库会永久保留该行。
`0009_price_multipliers` 是转换器唯一接受的退役 ID，且只能作为额外项出现；其他
未知 ID、重复项、乱序项或缺失的必填项都会被拒绝。

源**结构**对每张保留表双向固定：当前列必须全部存在，其他列只能是退役列
（`credentials.auth_state`、`credentials.auth_error_code`）。退役订阅表的结构
来自 `internal/storage/migrations/legacy_retired_schema.go`——逐字复现历史 DDL
的模型，转换器不再靠猜测判断真实旧库长什么样。

| 拒绝原因                                     | 含义                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------ |
| 台账不匹配                                   | 缺少必填项，或出现固定链与退役集合之外的 ID。                            |
| 存在未分类表                                 | 转换器既不迁移也不在删除清单里，拒绝猜测。                               |
| 列多出或缺失                                 | 声明的结构无法在本版本中复现。                                           |
| `-wal` 非空或存在 `-journal`                 | 仍有写入者持有数据库，或事务被中断；打开源库前与取快照后各检查一次。     |
| 缺少保留表                                   | 支持的旧结构声明的表不存在；强行拷贝会发布空表并静默丢失行。             |
| `integrity_check` / `foreign_key_check` 失败 | 源库损坏，需先修复或恢复。                                               |
| 存在订阅分组                                 | 分组使用退役连接类型（`subscription`、`oauth`）、已删除的订阅渠道（`codex`、`antigravity`、`grok`），或本版本已不再定义的渠道。 |
| 存在订阅表数据行                             | `credential_stages`、`credential_observations`、`credential_reset_operations` 中只要有任意一行。 |
| 存在订阅凭据状态                             | `credentials.auth_state` 不是 `ready`，或 `credentials.auth_error_code` 非空。 |

最后三条是刻意设计：订阅数据被拒绝而不是被静默删除。表检查看**行数**而不是可达性：
只要存了一行就拒绝，因为转换会丢弃这些表，存下的数据无法找回。空的退役表是
API-key-only 部署的正常状态，可以接受。只拷贝 `connection_type=api_key` 的分组。

写入者检测只是尽力而为的门槛，不是锁：空的 `-wal` 或 `-shm` 不算写入者（只读
打开本身就会创建），停旧实例仍是操作者的责任。该检查执行两次——打开源库前，
以及 `VACUUM INTO` 取快照后——因此转换中途才出现的写入者同样会被拦下。

发布结果是被证明的，不是被假设的：每张拷贝表都要与源库行数、主键集合一致；
目标库不得声明任何退役列；`AUTOINCREMENT` 计数器不得低于源库；且
`PRAGMA foreign_key_check` 与 `PRAGMA integrity_check` 都必须通过。任一项失败
即中止发布。

### 迁移与丢弃范围

迁移：`groups`、`credentials`（密文、指纹、`secret_version`、ID）、
`access_keys`、`access_key_cost_limit_rules`、`access_key_cost_limit_states`、
`system_settings`、`model_prices`、`control_operations`、`jobs`、
`agent_credentials`、`agent_change_proposals`。

不迁移且无替代：`request_logs`、`request_log_attempts`、
`credential_attempt_stats`、`credential_observations`、
`credential_reset_operations`、`credential_stages`、全部 `debug_capture*` 表、
`usage_stats`、`usage_attempt_stats`、`usage_aggregation_journal`、
`usage_attempt_aggregation_journals`、`schema_migrations`。退役列 `auth_state`、
`auth_error_code` 会被丢弃并在输出中列出。

`credential_attempt_stats` 是**丢弃而不是保留**：它是按凭据统计的尝试次数，和
周围的用量表一样属于历史，不要在转换后的库里期待它的数据。

发布出的库就是应用随后打开的库，首次启动会跑它自己的迁移链：台账是重建的，
不是拷贝的。拷贝同时保留每张表的 `sqlite_sequence` 高水位——旧库里被删除但仍被
旧请求日志、导出或备份引用的行 ID，不会被转换后的库重新分配出去。

### 密钥

转换后的库保存的是旧实例主密钥加密的凭据密文。必须把原密钥原样带到新
`DATA_DIR`：复制原 `encryption.key`，或在新环境沿用同一个 `ENCRYPTION_KEY`。
两者都没有时网关会生成新密钥并在加载凭据时报指纹不匹配，已有凭据无法解密。
如需保持管理密钥不变，再复制旧 `auth.key`（或沿用相同 `AUTH_KEY`）。

### 操作步骤

1. **确认源库。**先用**副本**跑一次转换。拒绝信息会指出不满足的前置条件：在旧
   实例上处理订阅分组后重试，或继续留在旧版本。不要手工改 `schema_migrations`
   或删表。
2. **停旧实例并确认无写入者。**停止容器（`docker compose -p gpt-load stop -t 30 gpt-load`），
   确认没有容器仍挂载该卷，且数据目录里没有非空 `-wal` 或 `-journal`。
3. **备份整个数据目录。**`gpt-load.db`、`-wal`、`-shm`、`auth.key`、
   `encryption.key` 以及 `.env`、`docker-compose.yml` 作为同一恢复集合归档，
   校验归档可读；空间与权限要求见
   [SQLite 运维与恢复](../../docs/sqlite-maintenance.md)。
4. **转换到新数据目录或新卷。**用新镜像、`--network none`、只读挂载备份目录，
   目标指向新目录，不要指向旧目录；先核对输出的分组、凭据、访问密钥行数。
5. **迁移密钥。**复制旧 `encryption.key` 到新数据目录，或沿用相同
   `ENCRYPTION_KEY`；不要让网关生成新密钥。
6. **在新卷上用新版本启动，先换一个端口**（例如 3101），确认日志出现
   `startup.ready` 且没有 `startup.failed`。
7. **切换流量前验证。**health 不等于验证：登录管理面；打开若干分组确认凭据可
   解密读取；各发一次非流式与流式真实请求；确认既有访问密钥可认证且限额用量与
   转换前一致；确认订阅渠道已不存在、分组模型未丢失。
8. **切换流量。**只有第 7 步通过后才在 ingress 改端口并切换客户端。
9. **回滚。**回滚是「旧镜像 + 完全未改动的旧卷」：按原端口重启旧容器并撤回
   ingress 改动。切换后新实例写入的数据**不会**合并回旧库；保留它们只能从旧库
   备份重新转换并人工修复，这不是受支持路径。

### 发布脚本边界

`scripts/deploy.sh` 只用于原地升级：它加载新镜像、停止容器、归档数据、改写
Compose 并在**同一个**现有卷上重启。它不转换数据库，因此本次升级不能把它指向
旧卷——新镜像只会拒绝启动。先完成转换，再让新版本部署到转换后的卷，并让旧卷和
旧备份保持在脚本的作用范围之外。
