判定规则

  • 收到 200 或第一个 token 不等于完成；必须获得对应协议的完整有效终态。
  • test_alias 更换了客户端模型名，权限过滤和参数覆盖可能因此不同；验证真实模型名时，使用“客户端路由”。
  • 上游 503 后切换候选并成功：客户端完成，第一条线路仍失败；中途已向客户端提交内容后，不拼接另一上游的答案。
  • 有效工具调用不要求可见文本；只证明模型返回了工具请求，不代表工具执行或任务完成。
  • 取消、流式断开与缺少终态显示“未完成”；日志缺失原文时不伪造重放。
  • 示例路由最多尝试两个候选，每个一次；这不是项目当前默认重试配置。

测活要回答的不是“2 + 2 有没有回复”

管理员的任务：接入一个模型后，确认自己的请求能用；出错后，定位是格式、授权、参数、上游还是路由问题。

建议范围

  1. 默认按实际请求测活。 从模型行进入时限定当前分组；从调度中心进入时使用客户端模型名。简单模板可直接运行，JSON 编辑按需使用。
  2. 旧固定测活保留为基础诊断。 不把旧结果叫作真实使用验证，也不删除凭据恢复能力。
  3. 结果保留上下文。 协议、流式、调用身份、模型映射、参数变化、attempt 与完成终态一起展示；不汇总成永久的“全功能可用”。
  4. 日志重放后续独立增加。 有原文且完成脱敏确认才创建测试草稿，不自动发送；缺原文允许新建模板，不称作重放。

本项目的事实边界

  • 现有 probe 固定短问题、非流式、不走普通参数覆盖；本页的真实请求工作区是拟议能力。
  • 已有 test_alias、真实执行器、请求日志、可选 debug capture 可复用；不再写一套“模拟真实请求”的后端。
  • 这次 input 报错仅有结构化日志和代码线索，没有原始通信。情境中的修复成功是模拟，不是线上复测结论。
  • 本期不扩展为评测平台、定时压测或工具执行器；真实客户端的动态 Header、SDK 行为仍需客户端验证。
